# 6-Step repeatable playbook
Treat it like a checklist with strict time boxes for a standard 45–60 minute interview.

---

### Step 1: Clarify & Scope (5 Minutes)

Don't try to design everything. Agree on a tight **v1 scope** with the interviewer and explicitly state what you are leaving out for now.

* **Ask 3–4 targeted questions** around actors, rules, and scale (e.g., *"Single floor or multi-floor? What happens when the lot is full? Is pricing flat or dynamic?"*).
* **Write down 4–5 bullet points of MVP requirements** at the top of your editor/whiteboard. This is your contract—if you get lost later, read these bullets.

### Step 2: Trace the Core User Journeys — *Before Writing Any Classes* (5 Minutes)

**This is the step most people skip, and it stops the "blank screen" panic.**
Before naming a single class, write 2–3 plain-English step-by-step flows of what actually happens in the system:

* **Flow 1 (Entry):** `Vehicle arrives at Gate -> System finds free matching Spot -> Marks Spot occupied -> Generates Ticket -> Returns Ticket.`
* **Flow 2 (Exit):** `Vehicle presents Ticket -> System calculates Fee using entry/exit time -> Marks Spot free -> Marks Ticket paid.`

Look at those two lines. You just discovered every single piece of state and every method your code needs before writing a line of Python.

### Step 3: Extract Nouns (Data Models) & Verbs (Logic/Managers) (5 Minutes)

Look directly at the words you just wrote in Step 2:

* **Nouns become dumb Data Classes (Models):** `Vehicle`, `ParkingSpot`, `Ticket`. Give them fields and simple state-change methods (like `spot.occupy()`), **no heavy business logic**.
* **Verbs become Service / Strategy Classes:**
* *"finds free matching Spot"* $\rightarrow$ `SpotAllocationStrategy`
* *"calculates Fee"* $\rightarrow$ `PricingStrategy`


* **The Orchestrator:** One main coordinator class (`ParkingLot`) that holds the collections and connects the flows from Step 2.

### Step 4: Write Skeleton Interfaces & Relationships First (10 Minutes)

Do **not** write full method implementations yet. Write empty class skeletons with:

1. `__init__` attributes (so the interviewer sees *who owns what*).
2. Method signatures with `pass` (so the interviewer sees *how classes talk to each other*).

**Why this saves you from dead ends:** If a relationship is wrong (e.g., you put `price` inside `Vehicle` instead of `PricingStrategy`), you spot it in 30 seconds while it's still empty skeletons—not after writing 100 lines of logic.

### Step 5: Implement the "Happy Path" End-to-End (15 Minutes)

Now fill in the `pass` blocks for your MVP flows from Step 2.

* Keep it simple first! Use basic lists/dicts (`O(N)` loop) so you have a **working, compilable system** on the board by minute 35.
* Write a quick 5-line `main()` / driver snippet at the bottom showing how objects are created and called. Interviewers love seeing your code actually wire together cleanly.

### Step 6: Layer on Complexity, Edge Cases & Concurrency (Last 10 Minutes)

Once the happy path works, **now** you optimize and harden it—either proactively or as the interviewer throws curveballs:

1. **Optimize bottlenecks:** *"Right now finding a spot is `O(N)`. To make it `O(log N)` for nearest spot, I'll swap in a Min-Heap per gate."*
2. **Edge cases:** Null inputs, capacity full, duplicate/invalid tickets, negative durations.
3. **Concurrency:** Identify shared mutable state (e.g., two gates claiming the same `ParkingSpot` or incrementing `ticket_id`) and wrap only that critical section in a `threading.Lock()`.

---

### Summary Cheat-Sheet to Keep in Mind

| Phase | Goal | Golden Rule |
| --- | --- | --- |
| **1. Scope** | 4–5 MVP bullets | Explicitly defer nice-to-haves to v2. |
| **2. Flows** | 2–3 step-by-step journeys | Never write classes before tracing the flow. |
| **3. Entities** | Nouns = Models, Verbs = Strategies | Keep data models thin; put rules in strategies. |
| **4. Skeletons** | Attributes + empty method signatures | Validate relationships before writing logic. |
| **5. Happy Path** | Working basic code + driver example | Get a working v1 first; don't prematurely optimize. |
| **6. Harden** | Heaps/Maps, Edge Cases, Locks | Add complexity only after v1 is solid. |
