# SOLID Principles in Object-Oriented Programming (OOP)

SOLID is a set of 5 design principles that help us write software that is:

- Easy to maintain
- Easy to extend
- Easy to test
- Less tightly coupled
- Less prone to breaking when requirements change

These principles are particularly important for Low-Level Design (LLD) interviews.

Let's understand each principle using Python, with a bad design, its problems, a better design, and an interview-ready explanation.

## Overview

| Principle | Full form                             | Main idea                                                      |
| --------- | ------------------------------------- | -------------------------------------------------------------- |
| S         | Single Responsibility Principle (SRP) | One class, one responsibility                                  |
| O         | Open/Closed Principle (OCP)           | Open for extension, closed for modification                    |
| L         | Liskov Substitution Principle (LSP)   | Child objects should work wherever parent objects are expected |
| I         | Interface Segregation Principle (ISP) | Don't force clients to depend on methods they don't need       |
| D         | Dependency Inversion Principle (DIP)  | Depend on abstractions, not concrete implementations           |

# 1. S — Single Responsibility Principle (SRP)

One class should have one reason to change.

A class should have one clearly defined responsibility.

### ❌ Bad example: Multiple responsibilities in one class

Imagine we are building an e-commerce application.

```
class Invoice:
    def __init__(self, items):
        self.items = items

    def calculate_total(self):
        return sum(item.price for item in self.items)

    def generate_pdf(self):
        print("Generating invoice PDF")

    def save_to_database(self):
        print("Saving invoice to database")
```

This class has three responsibilities:

1. Calculating the invoice total
2. Generating a PDF
3. Persisting the invoice to a database

Why is this problematic?

Suppose we change our PDF library. We need to modify `Invoice`.

Suppose we change our database. We need to modify `Invoice`.

Suppose our tax calculation changes. We also need to modify `Invoice`.

Three unrelated reasons to change = violation of SRP.

### ✅ Good example: Separate responsibilities

```
class Invoice:
    def __init__(self, items):
        self.items = items

    def calculate_total(self):
        return sum(item.price for item in self.items)


class InvoicePrinter:
    def generate_pdf(self, invoice):
        print("Generating invoice PDF")


class InvoiceRepository:
    def save(self, invoice):
        print("Saving invoice to database")
```

Now:

- `Invoice` handles invoice-related business logic.
- `InvoicePrinter` handles presentation.
- `InvoiceRepository` handles persistence.

Each class has a focused responsibility.

### Another real-world example

In a food delivery system:

| Class                 | Responsibility                 |
| --------------------- | ------------------------------ |
| `Order`               | Manage order details and state |
| `PaymentService`      | Process payments               |
| `NotificationService` | Send notifications             |
| `OrderRepository`     | Save and retrieve orders       |

Don't create one giant `OrderService` that handles everything.

### Interview explanation

> The Single Responsibility Principle states that a class should have only one reason to change. I achieve this by separating different concerns, such as business logic, persistence, and notifications, into separate classes. This improves cohesion, testability, and maintainability while reducing the impact of changes.

# 2. O — Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification.

This means when a new requirement comes in, we should ideally be able to add new behavior without modifying existing, stable code.

### ❌ Bad example: Using `if-elif` for every new payment type

```
class PaymentService:
    def pay(self, payment_type, amount):
        if payment_type == "credit_card":
            print(f"Paying {amount} using credit card")

        elif payment_type == "upi":
            print(f"Paying {amount} using UPI")

        elif payment_type == "paypal":
            print(f"Paying {amount} using PayPal")
```

Now the business asks us to support Google Pay.

We have to modify the existing `PaymentService` by adding another condition.

As payment methods increase, this class keeps growing. Modifying it can accidentally break existing payment methods.

### ✅ Good example: Use polymorphism

Define a common abstraction for payment methods.

```
from abc import ABC, abstractmethod


class PaymentMethod(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Paying {amount} using credit card")


class UPIPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Paying {amount} using UPI")


class PayPalPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Paying {amount} using PayPal")


class PaymentService:

    def process_payment(self, payment_method, amount):
        payment_method.pay(amount)
```

Usage:

```
payment_service = PaymentService()

payment_service.process_payment(
    CreditCardPayment(), 1000
)

payment_service.process_payment(
    UPIPayment(), 500
)
```

Now the business wants Google Pay.

We simply introduce a new class:

```
class GooglePayPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Paying {amount} using Google Pay")
```

And use it:

```
payment_service.process_payment(
    GooglePayPayment(), 2000
)
```

Notice: We didn't modify `PaymentService` at all.

### How does this work?

The key is abstraction + polymorphism.

`PaymentService` doesn't know which specific payment method it is dealing with. It only knows that the payment method supports `pay()`.

### Another real-world example

Suppose we have a notification system:

- Email notification
- SMS notification
- WhatsApp notification
- Push notification

Instead of repeatedly modifying a notification manager, each new notification type implements a common `Notification` interface.

### Interview explanation

> The Open/Closed Principle encourages us to design code that can accommodate new functionality without modifying existing tested code. I typically achieve this using abstractions and polymorphism. For example, instead of using conditional statements for each payment type, I define a common PaymentMethod abstraction and create separate implementations. Adding a new payment type then requires adding a new class rather than modifying the payment service.

# 3. L — Liskov Substitution Principle (LSP)

Objects of a child class should be substitutable for objects of their parent class without breaking correctness.

This is often the trickiest SOLID principle to understand.

Inheritance is not just about sharing code. It is about preserving behavioral expectations.

## ❌ Bad example: The classic Rectangle and Square problem

Let's define a rectangle:

```
class Rectangle:

    def __init__(self, width, height):
        self.width = width
        self.height = height

    def set_width(self, width):
        self.width = width

    def set_height(self, height):
        self.height = height

    def area(self):
        return self.width * self.height
```

Now let's inherit from it:

```
class Square(Rectangle):

    def __init__(self, side):
        super().__init__(side, side)

    def set_width(self, width):
        self.width = width
        self.height = width

    def set_height(self, height):
        self.width = height
        self.height = height
```

A square is mathematically a rectangle. So this inheritance may look correct.

But let's see what happens:

```
def calculate_area(rectangle):
    rectangle.set_width(5)
    rectangle.set_height(4)

    return rectangle.area()
```

For a regular rectangle:

```
rectangle = Rectangle(2, 3)
print(calculate_area(rectangle))  # 20
```

For a square:

```
square = Square(2)
print(calculate_area(square))  # 16
```

We expected an area of `5 × 4 = 20`, but got `16`.

Why?

Because changing the width of a square also changes its height. The `Square` violates the behavior expected from a `Rectangle`.

A child class should not introduce restrictions or surprising behavior that breaks code using the parent class.

## ✅ Good example: Avoid inappropriate inheritance

Instead, model them independently with a common abstraction:

```
from abc import ABC, abstractmethod


class Shape(ABC):

    @abstractmethod
    def area(self):
        pass


class Rectangle(Shape):

    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height


class Square(Shape):

    def __init__(self, side):
        self.side = side

    def area(self):
        return self.side * self.side
```

Now:

```
def calculate_area(shape: Shape):
    return shape.area()
```

Both classes can safely be passed to `calculate_area()`.

### Important LSP concepts

A subtype should preserve the guarantees of its parent:

- Preconditions: A child should not require stricter inputs than the parent.
- Postconditions: A child should not weaken the guarantees of the parent.
- Invariants: A child should preserve the parent's valid state and behavior.
- Exceptions: A child shouldn't introduce unexpected failures for valid parent usage.

### Another real-world example

Suppose a base class `Bird` defines:

```
class Bird:
    def fly(self):
        pass
```

Then we inherit:

```
class Penguin(Bird):
    def fly(self):
        raise Exception("Penguins cannot fly")
```

This is a design problem because client code expects every `Bird` to be able to fly.

A better design would be:

```
class Bird:
    pass


class FlyingBird(Bird):

    def fly(self):
        pass


class Sparrow(FlyingBird):
    pass


class Penguin(Bird):
    pass
```

Now the abstraction matches the actual behavior.

### Interview explanation

> Liskov Substitution Principle states that a subtype should be usable wherever its base type is expected without altering the correctness of the program. I focus on behavioral compatibility rather than just establishing an inheritance relationship. If a child class changes expected behavior, introduces stricter preconditions, or violates parent invariants, I would reconsider the inheritance hierarchy.

# 4. I — Interface Segregation Principle (ISP)

Clients should not be forced to depend on methods they do not use.

Instead of having one large interface that every class must implement, create smaller, focused interfaces.

## ❌ Bad example: A fat interface

Imagine we are building a machine interface:

```
from abc import ABC, abstractmethod


class Machine(ABC):

    @abstractmethod
    def print_document(self):
        pass

    @abstractmethod
    def scan_document(self):
        pass

    @abstractmethod
    def fax_document(self):
        pass
```

Now we implement a simple printer:

```
class BasicPrinter(Machine):

    def print_document(self):
        print("Printing document")

    def scan_document(self):
        raise NotImplementedError

    def fax_document(self):
        raise NotImplementedError
```

Our basic printer only supports printing. But we are forced to implement scanning and faxing too.

This creates unnecessary dependencies and meaningless implementations.

## ✅ Good example: Split the interfaces

```
from abc import ABC, abstractmethod


class Printer(ABC):

    @abstractmethod
    def print_document(self):
        pass


class Scanner(ABC):

    @abstractmethod
    def scan_document(self):
        pass


class Fax(ABC):

    @abstractmethod
    def fax_document(self):
        pass
```

Now implement different machines:

```
class BasicPrinter(Printer):

    def print_document(self):
        print("Printing document")


class AdvancedPrinter(Printer, Scanner, Fax):

    def print_document(self):
        print("Printing document")

    def scan_document(self):
        print("Scanning document")

    def fax_document(self):
        print("Faxing document")
```

Each class implements only the capabilities it actually supports.

### Another real-world example

In an e-commerce system, imagine:

```
class PaymentProcessor:
    def pay(self):
        pass

    def refund(self):
        pass

    def generate_invoice(self):
        pass
```

But some payment providers support payments only, while others support refunds as well.

Instead, we could split this into:

- `Payment`
- `Refundable`
- `InvoiceGenerator`

This lets classes implement only the capabilities they need.

### Interview explanation

> The Interface Segregation Principle states that clients should not be forced to depend on methods they don't use. I prefer smaller, cohesive interfaces over a single large interface. This avoids unnecessary implementations, reduces coupling, and makes adding new implementations easier.

# 5. D — Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules. Both should depend on abstractions.

This principle also states:

Abstractions should not depend on details. Details should depend on abstractions.

Let's break it down.

- High-level module: Business logic (e.g., order processing)
- Low-level module: Implementation detail (e.g., sending email, saving to MySQL)
- Abstraction: Interface or contract connecting them

## ❌ Bad example: Direct dependency on a concrete class

Suppose we build an order service.

```
class MySQLDatabase:

    def save(self, data):
        print("Saving data to MySQL")


class OrderService:

    def __init__(self):
        self.database = MySQLDatabase()

    def place_order(self, order):
        self.database.save(order)
```

What's wrong?

`OrderService` directly creates a `MySQLDatabase`.

Now suppose we want to switch to PostgreSQL, MongoDB, or an in-memory database for testing.

We must modify `OrderService`.

This creates tight coupling between business logic and infrastructure.

## ✅ Good example: Depend on an abstraction

Step 1: Define an abstraction.

```
from abc import ABC, abstractmethod


class Database(ABC):

    @abstractmethod
    def save(self, data):
        pass
```

Step 2: Implement different databases.

```
class MySQLDatabase(Database):

    def save(self, data):
        print("Saving data to MySQL")


class MongoDatabase(Database):

    def save(self, data):
        print("Saving data to MongoDB")


class InMemoryDatabase(Database):

    def save(self, data):
        print("Saving data in memory")
```

Step 3: Inject the dependency into the high-level class.

```
class OrderService:

    def __init__(self, database: Database):
        self.database = database

    def place_order(self, order):
        self.database.save(order)
```

Usage:

```
mysql = MySQLDatabase()
order_service = OrderService(mysql)

order_service.place_order({"item": "Laptop"})
```

Or:

```
mongo = MongoDatabase()
order_service = OrderService(mongo)

order_service.place_order({"item": "Laptop"})
```

Or for unit testing:

```
memory_db = InMemoryDatabase()
order_service = OrderService(memory_db)

order_service.place_order({"item": "Laptop"})
```

We don't need to change `OrderService` at all!

### What is Dependency Injection (DI)?

Notice this constructor:

```
def __init__(self, database: Database):
    self.database = database
```

We are passing the dependency from outside instead of creating it inside the class.

This is called Dependency Injection.

DI is a technique that helps us implement DIP. They are related, but not the same:

| DIP                              | Dependency Injection                  |
| -------------------------------- | ------------------------------------- |
| A design principle               | An implementation technique           |
| Defines what we should depend on | Defines how dependencies are provided |
| Depend on abstractions           | Inject dependencies from outside      |

### Another real-world example

In a notification system:

```
NotificationService
       |
       v
 Notification Interface
       |
       +------ EmailNotification
       |
       +------ SMSNotification
       |
       +------ WhatsAppNotification
```

`NotificationService` doesn't create an `EmailNotification` itself. It receives an implementation through its constructor.

### Interview explanation

> Dependency Inversion Principle states that high-level business logic should not directly depend on low-level implementation details. Both should depend on abstractions. I implement this using interfaces and dependency injection, which allows us to switch implementations easily and makes unit testing simpler because we can inject mocks or fakes.

# How all 5 SOLID principles work together

Let's take one practical example: an e-commerce checkout system.

Requirements:

1. Calculate the order total.
2. Process payment.
3. Save the order.
4. Send a confirmation notification.
5. Support new payment methods and notification providers in the future.

## Example architecture in Python

```
from abc import ABC, abstractmethod


# Abstraction: Payment
class PaymentMethod(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class UPIPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Paid {amount} through UPI")


class CardPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Paid {amount} through Card")


# Abstraction: Notification
class Notifier(ABC):

    @abstractmethod
    def send(self, message):
        pass


class EmailNotifier(Notifier):

    def send(self, message):
        print(f"Email sent: {message}")


class SMSNotifier(Notifier):

    def send(self, message):
        print(f"SMS sent: {message}")


# Abstraction: Repository
class OrderRepository(ABC):

    @abstractmethod
    def save(self, order):
        pass


class InMemoryOrderRepository(OrderRepository):

    def save(self, order):
        print(f"Order saved: {order}")


# High-level business logic
class CheckoutService:

    def __init__(
        self,
        payment: PaymentMethod,
        notifier: Notifier,
        repository: OrderRepository
    ):
        self.payment = payment
        self.notifier = notifier
        self.repository = repository

    def checkout(self, order):
        amount = order["amount"]

        self.payment.pay(amount)
        self.repository.save(order)
        self.notifier.send("Order placed successfully")
```

Usage:

```
checkout = CheckoutService(
    payment=UPIPayment(),
    notifier=EmailNotifier(),
    repository=InMemoryOrderRepository()
)

checkout.checkout({
    "item": "Laptop",
    "amount": 50000
})
```

### Which principle is applied where?

| Principle | Application                                                                                  |
| --------- | -------------------------------------------------------------------------------------------- |
| SRP       | Payment, notification, persistence, and checkout are separate responsibilities.              |
| OCP       | New payment or notification types can be added without modifying `CheckoutService`.          |
| LSP       | Any valid `PaymentMethod` can replace another without breaking checkout behavior.            |
| ISP       | Payment, notification, and repository abstractions are small and focused.                    |
| DIP       | `CheckoutService` depends on abstractions and receives dependencies through its constructor. |

This is what good LLD looks like: not just classes and inheritance, but a design that accommodates changing requirements.

# Common interview traps

| Misconception                                    | Correct understanding                                                                    |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| SRP means one method per class                   | No. A class can have many related methods.                                               |
| OCP means never modifying existing code          | No. Changes are sometimes necessary; the goal is to minimize changes for new variations. |
| LSP means every child must inherit from a parent | No. Inheritance should preserve behavioral contracts.                                    |
| ISP means create an interface for every method   | No. Interfaces should represent meaningful, cohesive capabilities.                       |
| DIP means always use dependency injection        | DI is a technique to achieve DIP, not the principle itself.                              |
| SOLID means more classes are always better       | No. Avoid unnecessary abstractions and overengineering.                                  |

# Quick revision for interviews

S — Single Responsibility

Does this class have multiple unrelated reasons to change?

O — Open/Closed

Can I add a new behavior without modifying existing stable code?

L — Liskov Substitution

Can I replace the parent with the child without breaking expected behavior?

I — Interface Segregation

Am I forcing a class to implement methods it doesn't need?

D — Dependency Inversion

Is my business logic coupled to concrete implementation details?

## My recommendation for your LLD preparation

When solving any LLD problem, don't try to force all five principles into your design. Instead:

1. Identify the core entities and responsibilities.
2. Identify what is likely to change (payment methods, pricing rules, notification channels, etc.).
3. Use interfaces and composition where appropriate.
4. Keep business logic independent of infrastructure.
5. Explain which SOLID principles your design naturally follows and why.

A great interview statement:

> I don't blindly apply SOLID everywhere. I use these principles to manage change, reduce coupling, and improve testability. I start with a simple design and introduce abstractions when I identify likely variations or concrete design problems.
